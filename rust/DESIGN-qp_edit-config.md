# `qp_edit` configuration format (D3)

Status: P2 design, implemented by `scripts/ezfio_interface/qp_edit_config.py`
(emission) and `rust/crates/qp-input` (consumption).  The hand-written
handler *bodies* are P4; this document defines their contract.

## Why a config file

Decision D3 makes `qp_edit` a **fixed binary**.  The set of editable sections,
their fields, types, defaults and help texts is read at run time from
`$QP_ROOT/data/qp_edit_config/`.  The files are generated by the existing
Python generator at build time from the same `EZFIO.cfg` sources that drive
the Fortran and OCaml code.  Consequences:

* adding or editing a field in an `EZFIO.cfg` regenerates the config only;
  the Rust binary is not recompiled, so it cannot drift from the source tree;
* the config directory is a **build artifact** and is gitignored
  (`data/.gitignore`), exactly like `data/ezfio_defaults/`;
* the seven behaviours that are not a field table (basis ordering, MD5,
  RST/sexp parsing, derived bit masks) stay imperative, in Rust, behind a
  named handler.

The OCaml files emitted by `ei_handler.py` are unchanged.  Their
byte-identity is checked by `scripts/ezfio_interface/test_dual_emission.py`
(see below).

## Files

```
data/qp_edit_config/
├── registry.toml          # ordered list of modules
├── ao_basis.toml          # one file per qp_edit section (37)
├── bitmasks.toml          # one derived handler module, section = false
└── ...                    # 38 module files in total
```

There is **one TOML file per module id**, and one module id per `[[module]]`
entry.  A `src/<dir>/EZFIO.cfg` can produce two files when the directory owns
a handler *and* declares `ocaml` fields: `src/ao_basis/` yields
`ao_basis.toml` (handler) and `ao_extra_basis.toml` (handler), while
`src/nuclei/` yields `nuclei_by_hand.toml` (handler) and `nuclei.toml`
(generic).  The two files describe the same EZFIO group but different
editing strategies; the generic file is what the engine shows, the handler
file documents what the handler owns.

## `registry.toml`

```toml
schema_version = 1

[[module]]
name = "nuclei_by_hand"
file = "nuclei_by_hand.toml"
section = true
handler = "nuclei_by_hand"

[[module]]
name = "ao_one_e_ints"
file = "ao_one_e_ints.toml"
section = true
```

| key | type | meaning |
|---|---|---|
| `schema_version` | integer | must equal `qp_input::SCHEMA_VERSION` (1) |
| `module` | array of tables | visit order |
| `name` | string | module id = file stem |
| `file` | string | bare file name inside the config directory |
| `section` | bool | whether `qp_edit` visits it as an editable section |
| `handler` | string, optional | owning handler; absent for generic modules |

Order is part of the contract:

1. `nuclei_by_hand`, `ao_basis`, `ao_extra_basis`, `electrons` — the
   hand-written sections that `qp_edit_template` visits first;
2. the generated modules, **sorted by name**;
3. `mo_basis`, `determinants_by_hand` — hand-written sections visited last;
4. `bitmasks` — the only `section = false` module.

The OCaml generator emits `Input_auto_generated.ml` in `os.listdir` order,
which is not reproducible.  The registry sorts step 2 deliberately, so the
build artifact is deterministic; the only visible consequence is the order of
sections in `qp_edit -w` output.  `test_dual_emission.py` builds a third tree
with the module directories created in reverse order and requires the config
directory to be byte-identical.

## `<module>.toml`

```toml
schema_version = 1
name = "electrons"
title = "Electrons"
section = true
handler = "electrons"
source_cfg = "src/electrons/EZFIO.cfg"
ezfio_dir = ["electrons"]

[[field]]
provider = "elec_alpha_num"
ezfio_name = "elec_alpha_num"
type = "Positive_int"
interfaces = ["ezfio", "provider"]
doc = "Numbers of electrons alpha (\"up\")"
size = "1"
editable = false

[[field]]
provider = "elec_num"
ezfio_name = "elec_num"
type = "Positive_int"
interfaces = ["ezfio"]
doc = "Numbers total of electrons (alpha + beta)"
size = "1"
default = "= electrons.elec_alpha_num + electrons.elec_beta_num"
default_is_formula = true
editable = false
```

| key | type | meaning |
|---|---|---|
| `schema_version` | integer | must equal 1 |
| `name` | string | must equal the registry entry and the file stem |
| `title` | string | RST header; non-empty iff `section` |
| `section` | bool | must equal the registry entry |
| `handler` | string, optional | must equal the registry entry |
| `source_cfg` | string | path relative to `$QP_ROOT`; never absolute |
| `ezfio_dir` | array of 1 string | the EZFIO group written by this config |
| `field` | array of tables | EZFIO providers, in `EZFIO.cfg` order |

Field keys:

| key | type | meaning |
|---|---|---|
| `provider` | string | provider name (`[section]` of `EZFIO.cfg`) |
| `ezfio_name` | string | key inside the EZFIO group (`ezfio_name:`) |
| `type` | string | declared type, **verbatim** |
| `interfaces` | array of strings | subset of `ezfio`, `provider`, `ocaml` |
| `doc` | string | help text, verbatim (RST markup kept) |
| `size` | string | `"1"` for a scalar, `"(ao_basis.ao_num,3)"` for an array |
| `default` | string, optional | default value as rendered for OCaml |
| `default_is_formula` | bool, optional | default starts with `=` (Fortran) |
| `editable` | bool | generic engine may change it |

`editable` is true exactly when the module is generic (no handler) and the
field declares the `ocaml` interface.  Handler modules list all their fields
with `editable = false`: the handler owns the whole section, including values
the generic engine would otherwise show.

The loader (`qp_input::loader`) enforces every rule above.  Unknown keys are
rejected (`deny_unknown_fields`): a generator change that the binary does not
understand must fail at start-up, not be silently ignored.

### Types

`type` is the declared spelling from `EZFIO.cfg`, not a normalised enum.  The
binary maps it through a 52-entry table
(`rust/crates/qp-input/src/types.rs`) copied from
`ocaml/qptypes_generator.ml` via `ei_handler.get_type_dict`.  Each entry
gives the primitive storage (`int`, `float`, `bool`, `string`) and a domain:
inclusive/exclusive numeric bounds, case-insensitive choices, `MO_class`
keyword, 32-character MD5, or non-empty string.

Two deliberate differences from the OCaml implementation are documented at
the table:

* plain `integer` is range-checked to 32 bits (its Fortran storage width;
  OCaml uses a 64-bit `int`);
* `MO_occ` values outside `[0, 2]` are rejected instead of silently clamped.

`%s` appears in the Python dictionary only as a parsing artifact of
`qptypes_generator.ml` and is not a type; it is absent from the Rust table.

Defaults are stored as TOML **strings** and parsed only for literal values.
A default starting with `=` is a Fortran expression; it is kept verbatim,
flagged with `default_is_formula = true`, and the loader refuses to use it as
a value.  Three fields are in that situation in the current tree
(`ao_basis.ao_prim_num_max`, `ao_extra_basis.ao_prim_num_max`,
`electrons.elec_num`); `qp_edit --check-config` prints them as warnings and
the owning handler (or the Fortran side) must supply the value.

### What the config does *not* contain

* **Units.** No `EZFIO.cfg` declares units and no other source in the tree
  does either; inventing them would be worse than omitting them.  Plan §3.2
  lists units as config content; this is a plan/implementation discrepancy,
  not an oversight.
* **Ranges and choices as data.** They are not present in `EZFIO.cfg`; they
  live in `qptypes_generator.ml`, which is OCaml code, and are therefore
  compiled into the binary's type table.  A type added there needs a one-line
  Rust table entry (a code change), not a config regeneration.
* **Check/apply semantics.** They are code: the generic engine applies a
  field through `qp-ezfio`; the handlers implement their own check/apply.
  Making them data would require a small interpreter and buys nothing for
  seven sections.

## Config-vs-code split

| in the TOML (build artifact) | in the binary (compiled) |
|---|---|
| module list and order | discovery and loading |
| section title, `section`, handler name | engine REPL, apply/check path (P4) |
| field names, EZFIO keys, docs | prompt layout, validation messages |
| declared type spelling | type parsing/validation table |
| size expression (verbatim) | array/scalar distinction, dimension resolution (P4) |
| literal default, formula flag | default parsing, handler-supplied defaults |
| `editable` | handler dispatch and behaviour |

The only duplicated knowledge is the seven handler names and their section
titles.  The generator keeps the titles in `qp_edit_config.HANDLER_MODULES`,
and `check_template_consistency()` parses the `keyword_to_string` table of
`qp_edit_template` to assert equality; `test_dual_emission.py` runs it.  The
names are checked by the Rust unit test `handlers::tests` and by the loader
(unknown handler, handler/module id mismatch, handler/section mismatch).

## Handlers

| handler | module id | section | OCaml source | owns |
|---|---|---|---|---|
| `nuclei_by_hand` | `nuclei_by_hand` | yes | `Input_nuclei_by_hand.ml` | molecule from RST: atoms, coordinates, charge, Z-matrix |
| `ao_basis` | `ao_basis` | yes | `Input_ao_basis.ml` | AO basis ordering, `ao_basis.md5` consistency |
| `ao_extra_basis` | `ao_extra_basis` | yes | `Input_ao_extra_basis.ml` | auxiliary basis, same MD5 rules |
| `electrons` | `electrons` | yes | `Input_electrons.ml` | `elec_num`, alpha/beta spin, derived occupations |
| `bitmasks` | `bitmasks` | **no** | `Input_bitmasks.ml` | `n_int` from `mo_num`, `bit_kind` from the build |
| `mo_basis` | `mo_basis` | yes | `Input_mo_basis.ml` | MO ordering, MD5 comparator, consistency |
| `determinants_by_hand` | `determinants_by_hand` | yes | `Input_determinants_by_hand.ml` | determinant list from RST and sexp |

`bitmasks` is emitted with `section = false` because `Input.ml` includes it
but `qp_edit` never visits it; its values are a dependency of the
determinants handler.  The module id is plural (`bitmasks`) while the
directory is singular (`src/bitmask/`), matching the tracked OCaml file name.

The contract between generator and binary is exactly: the `handler` string is
one of the seven names above, and it is attached to the module whose id
equals it.  The handler implementations are P4 work; `crates/qp-input` only
declares the enum.

## Discovery

`qp_input::loader::discover(explicit, env, exe_dir)` implements D3:

1. `--config <dir>`;
2. `$QP_EDIT_CONFIG`;
3. `<exe_dir>/../data/qp_edit_config` (installed layout
   `$QP_ROOT/bin/qp_edit`).

The first candidate wins and must be an existing directory; failure names
which origin was used.  The function is pure (the caller reads the
environment and `current_exe`), because `std::env::set_var` is `unsafe` in
edition 2024 and because precedence is then unit-testable.

## Emission and the build

`ei_handler.py --ocaml` calls `qp_edit_config.emit_module(...)` after the
existing OCaml/default writers.  The call sits **outside** the
`try: create_ocaml_input() except ValueError` guard: `ao_basis`,
`electrons` and `mo_basis` have no `ocaml`-interface field (so the OCaml
writer raises and skips them) but they still own handler sections.
`ei_handler.py ocaml_global` calls `qp_edit_config.save_registry(...)` after
writing `qp_edit.ml` and `Input_auto_generated.ml`.

Emission is never triggered by the plain Fortran targets: the call is inside
the `--ocaml` / default-all branch of `code_generation`.

P5 adds the ninja rule.  The intended shape (not implemented in P2) is:

```ninja
rule qp_edit_config
  command = cd $root && $python $root/scripts/ezfio_interface/ei_handler.py --path_module $in
  description = qp_edit config $module

# one build edge per EZFIO.cfg, plus the registry edge:
build $root/data/qp_edit_config/registry.toml: qp_edit_config_registry
  # runs `ei_handler.py ocaml_global` from $root/ocaml
```

with each module edge declaring `$root/data/qp_edit_config/<module>.toml` as
its output and depending on `EZFIO.cfg` + the two generator scripts, and the
registry edge depending on all module outputs.  `data/qp_edit_config/` stays
gitignored.

## Migration

1. P2 (this change): generator dual-emits, Rust loader and prototype binary
   exist, OCaml output is byte-identical (163 files compared).
2. P4: the seven handlers and the REPL/apply/check path replace
   `ocaml/qp_edit.ml`; `data/qp_edit_config/` is the only source of section
   metadata.
3. P5: ninja builds the config and installs the binary under `$QP_ROOT/bin`.
4. After the OCaml `qp_edit` is removed, `qp_edit_template` and the hard-coded
   `keyword_to_string` table disappear; the title duplication noted above
   goes away with them.

Because the config is a build artifact, nothing is committed and no generated
TOML can go stale: a clean build always regenerates it from the checked-in
`EZFIO.cfg` files.

## Testing

* `cargo test -j4` — schema round-trip, loader rejection cases, type table,
  handler names, engine output, and the binary's exit codes (36 tests).
* `cargo clippy --all-targets -- -D warnings`, `cargo fmt --check`.
* `python3 scripts/ezfio_interface/test_dual_emission.py --pristine-ref
  b0eae6e2 --qp-edit rust/target/debug/qp_edit` — builds three isolated
  `$QP_ROOT` trees (modified, pristine, reverse creation order), runs the
  generator for all 43 `src/*/EZFIO.cfg` modules plus `ocaml_global`, diffs
  every generated OCaml/EZFIO/default file, validates all 38 config files,
  and runs `--check-config`.

Complexity: loading is O(number of fields) with one binary search per field
over a 52-entry table; memory is the parsed config (353 field tables today).
`--check-config` is I/O-bound (39 small files).
