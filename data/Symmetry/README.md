Character tables of the point groups
====================================

One file per point group, read by the ``symmetry`` module
(``src/symmetry/chartab.irp.f``). The file name **is** the group name: the
detector identifies a group by its measured invariants, builds a name, and
opens ``$QP_ROOT/data/Symmetry/<name>``. There is no override: the directory
is the one of the installation that runs the code, and ``QP_ROOT`` must be set
when the module is loaded.

Provenance
==========

These files were generated by the author of the symmetry module
(A. Scemama) on 2026-11-02 as part of developing it. They are original data:
they are **not** copied from a printed character-table compilation, so no
third-party copyright applies and they are distributed with Quantum Package
under the licence of this repository.

The generating script was not kept. The set is therefore *fixed data*: it is
extended by adding a file, never by regenerating the whole directory. Every
table is validated before it is used -- syntax when it is opened, semantics
against the enumerated group right after -- so a bad file is rejected with a
message instead of being used silently (see "Validation" below).

Format
======

Tabs separate the fields; the notation below is exact (``\t`` is a tab).

1. ``Group\t<name>`` -- informational only; the detector does not read it.
   (``Dinfh`` deliberately carries a name the module cannot produce.)
2. ``n\t<n>`` -- ``n`` is the number of irreps, which equals the number of
   classes. It is **not** the order of the group: ``D6h`` has ``n = 12``
   irreps and order 24.
3. A blank line.
4. A header line containing both ``Irred`` and ``Operation``.
5. ``n`` lines: ``<i>\t<irrep name>\t<operation symbol>``, with
   ``i = 1..n`` in order. The name is what the user sees (``A1``, ``B3u``,
   ``Sigma+``, ...), the symbol is a representative element of class ``i``.
6. Blank lines, then ``Table``.
7. A column-index line of ``n`` integers (present, skipped).
8. ``n`` lines of ``n`` fixed-format numbers: row ``i`` is the row of irrep
   ``i``, in the order of step 5, and gives its character on each class, in
   the order of step 5.

A worked example, ``C2v``::

    Group	C2v 
    n	4

         	Irred     	Operation
       1 	 A1         	 E         
       2 	 A2         	 C2        
       3 	 B1         	 sv        
       4 	 B2         	 sd        

    Table
             1         2         3         4      
       1   1.00000   1.00000   1.00000   1.00000  
       2   1.00000   1.00000  -1.00000  -1.00000  
       3   1.00000  -1.00000   1.00000  -1.00000  
       4   1.00000  -1.00000  -1.00000   1.00000  

The column of a class is found by **parsing its symbol**, not by its
position, so a table may list the classes in any order as long as the
symbols are the ones the detector emits: ``E``, ``Cn``, ``Cn^k``, ``S n``,
``i``, ``sv`` (plane ``xz``, normal ``y``), ``sd`` and ``s`` (plane ``yz``,
normal ``x``; ``sd`` is the other vertical class when ``sv`` is taken),
``sh`` (plane ``xy``, normal ``z``), ``C2'`` (the class through ``x``),
``C2"`` (the remaining one). When a group has a single vertical reflection
class, ``s``/``sv``/``sd`` all select it: only two or more classes force the
symbol to be resolved.

Validation
==========

``chartab.irp.f`` checks the syntax while reading: the two header lines, the
blank line, the ``Irred``/``Operation`` header, the ``i = 1..n`` sequence,
the ``Table`` marker, the ``n x n`` shape, and that nothing but blanks
follows the last row.

The content is then checked against the **enumerated** group, not against
itself (``columns.irp.f``): every class must match exactly one column symbol,
the characters must satisfy $\sum_c |c|\,\chi_a(c)\chi_b(c) = |G|\,m_a\,
\delta_{ab}$, the dimensions must satisfy $\sum_a d_a^2/m_a = |G|$, and they
must be multiplicative over direct products. A table failing one of these is
reported with the relation that failed and the run continues without symmetry
labels instead of aborting. ``|c|`` is the number of elements of the class,
``d_a = chi_a(E)`` and ``m_a`` is 2 when the table row is the sum of a
complex-conjugate pair of irreps (``C3``, ``C10``, ...) and 1 otherwise; that
is why the ``E`` irrep of ``C3`` enters as ``d^2/m = 4/2``.

Files present but never selected
================================

``C1h``, ``C1v``, ``D1``, ``D1d`` and ``D1h`` are the ``n = 1`` cases where
two standard names collapse onto one group. The naming tree produces the
surviving name (``Cs``, ``Cs``, ``C2``, ``C2h``, ``C2v``), so these five files
are never opened. ``Cinfv`` and ``Dinfh`` are linear-molecule groups:
detection refuses a linear molecule before any table is read, so they are
never opened either. They are kept for completeness of the family set, and
both carry a defect that must be fixed before anyone tries to use them:

* ``Cinfv`` is a correct ``C31v`` table (62 elements, 17 classes) whose rows
  are renamed ``Sigma+``, ``Sigma-``, ``Pi``, ``Delta``, ``Phi``, ``Gamma``,
  ``E5`` ... ``E15``. Those names are right for the 31 sampled rotations, so
  the body is usable as is.
* ``Dinfh`` is **not** a ``Dinfh`` table. Its body is the ``D32h`` body --
  identical to the file ``D32h``, down to the ``Group`` line, which says
  ``D32h`` -- with some rows renamed. Rows 3, 4, 22 and 23 keep the ``D32h``
  names ``B1g``, ``B2g``, ``B1u``, ``B2u``, which do not exist in any
  ``Dinfh`` character table: their characters are defined on the ``C2'`` and
  ``C2"`` columns, two classes that ``Dinfh`` does not have (all its
  perpendicular two-fold axes are one class). Reading a ``Dinfh`` label off
  them duplicates ``Sigma_g+`` and ``Sigma_g-``. A finite model of ``Dinfh``
  with only valid labels is ``D31h`` = ``C31v`` x ``Ci`` (34 irreps). Neither
  file has ever been checked against the reference implementation, which skips
  both.
